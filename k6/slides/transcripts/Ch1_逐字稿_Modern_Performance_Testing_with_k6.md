### 【Slide 2: 極致資源利用率：為什麼 k6 單機就能榨出數萬併發？】 (預估時間: 03:00 - 05:00)

* **畫面焦點**：對比圖：上方為傳統 Java OS Thread 臃腫的排隊與垃圾回收（GC）卡頓；下方為 Go Goroutine 輕量、密集的協程矩陣。
* **螢幕動作**：【動作：圈選 Java 執行緒的 1MB 標註，隨後指向 Go Goroutine 的 2KB 標註，並口頭補充「一個 k6 VU 實際約 1~5MB」】。

**【口播逐字稿】**：
> 「這時候，很多有經驗的工程師通常會提出一個直覺的質疑：『老師，既然 k6 是用 JavaScript 寫的，那它的效能真的撐得住高併發嗎？Node.js 在處理密集計算時不是很容易卡住嗎？』  
> 
> 這就是 k6 設計最精妙的架構底層！大家請記住這句話：**k6 只有腳本語法層是 JavaScript，底層真正的執行引擎，完全是用 Go 語言打造的！**  
> 
> 我們來看這張架構對比圖。在傳統基於 JVM 的壓測工具中，通常採用『One Thread per VU』的模式——也就是一個虛擬用戶（Virtual User, VU），就對應一條作業系統層級的原生執行緒（OS Thread）。每條執行緒光是記憶體堆疊（Stack Size）就要預先分配 1MB 到 2MB。如果你想模擬 5,000 個虛擬用戶，光是執行緒本身的記憶體開銷就高達 5GB 到 10GB！機器很快就會因為記憶體不足（OOM）而崩潰，更不用提作業系統在數千條執行緒之間頻繁進行 Context Switch（上下文切換）所造成的嚴重 CPU 耗損與 GC 停頓。  
> 
> 而 k6 徹底拋棄了傳統執行緒模型，改為全面利用 Go 語言的核心武器——**Goroutine（輕量級協程）**。  
> 每個 Goroutine 的初始堆疊只有大約 2KB 到 4KB，並且由 Go Runtime 的排程器在使用者空間高效調度，Context Switch 的成本遠低於 OS 執行緒。  
> 
> 不過這裡我要特別澄清一個很常見的誤解：**一個 k6 VU 並不等於一個 2KB 的 Goroutine。** 每個 VU 都帶著自己獨立的 JavaScript Runtime、載入的模組與資料，所以官方文件給的估算是：簡單腳本每個 VU 大約 1 到 5MB，1,000 個 VU 大約需要 1 到 5GB 記憶體。k6 真正的優勢在於排程輕量、CPU 效率高，官方數據是一台高規格機器可以跑到三到四萬個 VU。所以實務建議是：先用 100 個 VU 實測記憶體，再等比例推估你需要多大的壓測機！」

### 【Slide 5: 掌握執行順序：k6 腳本的 4 階段生命週期】 (預估時間: 09:30 - 11:30)

* **畫面焦點**：四個循序排列的彩色區塊：`1. Init Context` $\rightarrow$ `2. Setup Context` $\rightarrow$ `3. default function` $\rightarrow$ `4. teardown()`。特別標記「執行 1 次」與「每 VU 重複執行」。
* **螢幕動作**：【動作：由上至下逐一指引四個區塊，在第 1 區塊強調禁止發送 HTTP 請求】。

**【口播逐字稿】**：
> 「掌握了架構與 AI 工作流之後，我們要進入寫腳本的核心心法——**k6 的 4 階段生命週期 (Lifecycle)**。  
> 很多初學者寫 k6 腳本之所以會出錯，八成都是因為把代碼放錯了生命週期階段。請大家跟我一起把這四個階段看清楚：  
> 
> 第一階段，叫做 **Init Context（初始化階段）**。這是腳本最外層的全域範疇。當 k6 啟動時，它會在這個階段載入所有 `import` 模組、讀取靜態檔案（如 `open()`），或是定義匯出的 `options`。請特別注意：**Init 階段每個 VU 只會在啟動時執行一次，而且嚴禁在這個階段發送任何 HTTP 請求！** 如果你在全域寫了 `http.get()`，k6 會直接報錯拒絕啟動。  
> 
> 第二階段，是 **setup()（準備階段）**。你只要在腳本中導出一個叫做 `setup()` 的函式，k6 就會在整個壓測開始前、所有 VU 尚未發動時，**全域只執行一次**。這非常適合拿來做前置作業，例如：呼叫一次認證 API 取得全域 Token/Cookie、向測試資料庫建立初始種子帳號，然後把這些資料 `return` 出去，可傳遞給下一步的 VU 使用。  
> 
> 第三階段，是 **default function（預設執行階段）**。這就是我們導出的 `export default function (data)`。這是整個壓測的核心引擎！所有的虛擬用戶，都會在我們設定的測試時間內，依照頻率反覆迴圈執行這個函式裡的邏輯。你發送真實的壓測流量、發送 API 請求、做資料檢驗、模擬使用者思考時間，全部都在這個階段。  
> 
> 最後第四階段，是 **teardown()（環境清理階段）**。當所有 VU 測試時間結束、全部退場之後，k6 會**全域執行一次** `teardown(data)` 函式。你可以拿它來清理剛才產生的暫存資料、復原測試環境，或是整合外部系統發送 Webhook 通知。  
> 
> 清楚劃分這四個階段，你的腳本結構就會極其清晰，永遠不會發生在迴圈裡重複做昂貴初始化動作的低級錯誤。」

**【口播逐字稿】**：
> 「接下來是很多單元測試背景工程師最容易踩的坑——**斷言機制的本質差異**。  
> 
> 在單元測試中，我們習慣使用 `assert(response.status === 200)`，一旦條件不符合，程式立刻拋出 Exception、腳本崩潰中斷。這在單元測試完全正確，但在高併發壓測中卻是一場災難！試想：如果系統在 10,000 個請求中偶發了 1 次 500 錯誤，你希望整個壓測當場暴斃停機，還是希望它繼續把剩下的 9,999 個請求打完，精確統計出系統的成功率是 99.99%？  
> 答案顯然是後者！這就是為什麼 k6 的 `check()` 被設計為**軟性斷言（Soft Assertion）**。  
> 它的核心觀念是用於驗證 HTTP 狀態碼或 Response 時間。它就像畫面中的半透明感應門一樣，哪怕檢查失敗，虛擬用戶依然會繼續執行後續代碼，k6 只會在背景默默將失敗記錄於 `checks` 指標中，確保壓力持續產生。  
> 
> 如果你真的想在錯誤率過高時中斷 CI/CD，該怎麼辦？別急，這就是我們在 Chapter 3 會深入探討的硬門禁——Thresholds。」

### 【Slide 8: 防範記憶體炸彈：使用 http.url 處理動態 URL】 (預估時間: 15:30 - 17:30)

* **畫面焦點**：上方展示動態 ID 痛點（`/users/1`, `/users/2`...）引發時間序列爆炸與 OOM 警告；下方展示使用 `http.url` 標籤函數如漏斗般將動態請求聚合為單一名稱。
* **螢幕動作**：【動作：圈選上方紅色警告框與下方綠色漏斗聚合圖】。

**【口播逐字稿】**：
> 「大家請坐正，接下來這頁投影片，價值百萬！這是很多資深團隊導入壓測時，一不小心把公司內部監控系統直接打掛的真實慘痛案例。  
> 
> 我們很常測試 RESTful API，路徑中常常帶有動態參數，例如 `/api/orders/${orderId}` 或是 `/api/users/${userId}`。  
> 很多新手很直覺地寫下字串拼接：`http.get('/api/users/' + id)`。當你用 1,000 個 VU 打了 10 萬次請求，每個請求的 URL 都長得不一樣。k6 在預設情況下，會將每個獨立 URL 視為不同標籤，為每一個 URL 字串在記憶體中建立一條全新的時間序列指標！  
> 這會引發嚴重的**動態 ID 痛點（Metrics High Cardinality Explosion）**！如果你的 k6 同步將指標推送到 Prometheus 或 Datadog，數十萬條毫無意義的時間序列會瞬間灌爆記憶體，直接導致整個公司的 Grafana 與監控叢集 OOM 當機！  
> 
> k6 為我們提供了非常優雅的解決方案：**http.url 最佳實踐**。  
> 大家看綠色區塊的寫法：只要在樣板字面值前面加上 `http.url`，例如 ``http.url`https://api.example.com/users/${userId}` ``，k6 會在底層自動將請求的統計指標聚合為單一名稱 `/users/${userId}`，大幅降低記憶體開銷。  
> 記住這個小技巧，你就能在享受動態測試資料的同時，確保可觀測性監控系統永遠健康穩定。」
