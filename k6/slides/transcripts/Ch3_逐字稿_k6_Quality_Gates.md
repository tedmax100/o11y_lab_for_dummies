### 【Slide 2 (原S3): 一眼看穿系統健康度：RED Method】 (預估時間: 01:45 - 03:45)

* **畫面焦點**：左側展示 k6 終端機真實報告，右側以高亮引導線對齊 RED Method 三大黃金維度（Rate, Errors, Duration）。
* **螢幕動作**：【動作：依序圈選終端機報告中的 `http_reqs`、`http_req_failed` 與 `http_req_duration`】。

**【口播逐字稿】**：
> 「當你執行完 k6，控制台會印出密密麻麻的摘要。很多新手一看到這整片輸出就頭皮發麻，不知道重點在哪裡。  
> 請大家記住這個在微服務架構中無人不知的黃金觀測法法則——**RED Method**：  
> 
> 第一個字母 **R 代表 Rate（請求速率）**：  
> 對應終端機裡的 `http_reqs`。它告訴我們系統在測試期間一共處理了多少次請求，以及平均每秒處理的請求數（例如畫面上的 49.55/s）。這衡量的是系統的吞吐能力。  
> 
> 第二個字母 **E 代表 Errors（錯誤率）**：  
> 對應終端機裡的 `http_req_failed`。它統計了非預期的 HTTP 狀態碼（例如 4xx、5xx）佔整體請求的百分比。畫面上的 0.00% 代表所有請求在通訊層面全數成功。  
> 
> 第三個字母 **D 代表 Duration（回應延遲）**：  
> 對應終端機裡的 `http_req_duration`。它記錄了從請求送出到完整收下回應所花費的時間。  
> 
> 任何系統的效能體檢，首先看這三兄弟！如果 Rate 很高、Errors 是 0，但 Duration 異常膨脹，你就知道系統已經逼近飽和拐點。掌握 RED Method，你就掌握了閱讀效能報表的第一把鑰匙。」

### 【Slide 3 (原S4): 破解平均值陷阱：尾端延遲與百分位數】 (預估時間: 03:45 - 06:15)

* **畫面焦點**：平均值（Average）隱瞞真相圖解，對比 P95、P99 尾端延遲在常態分佈長尾中的關鍵位置。
* **螢幕動作**：【動作：語氣嚴肅，圈選 Average 的假象與 P99 的紅區】。

**【口播逐字稿】**：
> 「大家請看畫面上的警告標誌。身為專業的效能工程師，請大家在心中牢牢刻下一條鐵律：**永遠不要拿平均值（Average）向主管或客戶報告！**  
> 
> 為什麼？我們來看一個真實案例：  
> 假設有 100 位顧客到你的電商網站購物。其中 99 位顧客在首頁隨意逛逛，API 回應速度極快，只要 10 毫秒；但偏偏有 1 位顧客要把 10 萬元的商品送出結帳，結果系統因為資料庫鎖定，卡了整整 10 秒鐘！  
> 現在，我們把這 100 個數據加起來算數學平均值——$(99 \times 0.01 + 10) / 100 \approx 0.109$ 秒，也就是大約 109 毫秒！  
> 報表交上去，大家皆大歡喜：『哇，平均延遲才 0.1 秒，系統超順暢！』但事實是什麼？事實是那個真正要掏錢買單的大客戶，在螢幕前乾等了 10 秒鐘，最後氣得直接把分頁關掉、去競品網站下單了！  
> 
> 這就是**平均值陷阱**！在現代高併發分散式架構中，平均值會徹底掩蓋嚴重的長尾問題。  
> 我們必須看**百分位數（Percentiles）**：  
> - **P90**：代表全體請求中有 90% 優於這個時間；  
> - **P95**：代表 95% 的請求都達標，是業界最通用的日常驗收基準；  
> - **P99（尾端延遲，Tail Latency）**：它精準捕捉了那最倒楣、體驗最差的 1% 用戶！在高併發微服務鏈路中，一個複雜頁面可能要打 20 支 API，只要其中一支命中 P99，整個前端就會卡死。  
> 因此，從今天開始，我們設定所有 SLO 門檻，一律以 P95 或 P99 為唯一依據！」

### 【Slide 4 (原S5): k6 內建核心指標全覽】 (預估時間: 06:15 - 08:30)

* **畫面焦點**：`http_req_duration` 的精密時間軸拆解：blocked $\rightarrow$ connecting $\rightarrow$ tls_handshaking $\rightarrow$ sending $\rightarrow$ waiting (TTFB) $\rightarrow$ receiving。
* **螢幕動作**：【動作：由左至右滑動解析各個網路階段】。

**【口播逐字稿】**：
> 「既然 Duration 這麼重要，那當 Duration 飆高時，我們該如何抽絲剝繭找原因？  
> k6 非常貼心地把單次 HTTP 請求細剖成了六個階段：  
> 
> 1. **blocked**：請求發送前，在作業系統連線佇列中等待可用 TCP Socket 的時間；  
> 2. **connecting**：與目標伺服器進行 TCP 三向交握（SYN-ACK）的網路耗時；  
> 3. **tls_handshaking**：HTTPS 憑證協商與金鑰交換的加密耗時；  
> 4. **sending**：將 HTTP 請求 Header 與 Body 資料透過網卡推送出去的傳輸耗時；  
> 5. **waiting（核心重點！）**：又稱 **TTFB (Time to First Byte)**！這是從客戶端把請求發送完畢，到收到伺服器吐出第一個 Byte 的等待時間。這段時間伺服器在幹嘛？它在跑業務代碼、在查資料庫、在呼叫第三方服務！如果你的 API 延遲飆高，有 80% 的機率是卡在 waiting；  
> 6. **receiving**：伺服器吐出資料後，客戶端把整個 Response Body 下載完畢的時間。  
> 
> 如果有一天你發現 waiting 只有 20ms，但 duration 高達 2 秒，receiving 佔滿了 1.9 秒，這代表什麼？這代表後端計算極快，但它愚蠢地把幾十萬筆沒做分頁的資料一口氣丟給前端！透過這六大指標，你甚至不用看後端代碼，就能在第一時間精準定位架構病因。  
> 不過要特別注意：這六段**並不全部**算在 `http_req_duration` 裡，這個常見誤解我們等一下在 Slide 6 專門拆解。」

### 【Slide 5 (新增): 看懂 k6 結尾摘要：5 步驟判讀 SOP】 (預估時間: 08:30 - 11:00)

* **畫面焦點**：左側深色終端機是一份「有問題」的結尾摘要，右側 5 張卡片是判讀順序 ①～⑤，底部是本例結論。
* **螢幕動作**：【動作：依 ①→⑤ 順序，逐一把游標從左邊終端機的 ◀ 標記移到右邊對應卡片】。

**【口播逐字稿】**：
> 「認識了這麼多指標，接下來是最實用的問題：測試跑完，終端機吐出一大段摘要，**你到底該怎麼讀？**  
> 新手最常犯的錯，是從第一行讀到最後一行，或者瞄一眼綠色勾勾就收工。資深工程師會帶著問題，照固定順序讀，一共五步。  
> 
> **第一步，看 THRESHOLDS，這是判決書。** 只回答一個問題：過關了沒？這份摘要的 `p(95)<500` 打了紅色叉叉，實際 812 毫秒。只要有一個叉，k6 就會以 Exit Code 99 結束。記下是哪個指標違規，後面每一步都在找「為什麼」。  
> 
> **第二步，看 checks，檢查功能正確性。** 成功率 99.58%，往下看是 `status is 200` 失敗了 25 次。提醒大家：check 是軟斷言，失敗不會讓 CI 失敗，要擋就得另外加 checks 門檻。  
> 
> **第三步，看 HTTP 群組，讀出分佈的形狀。** 不要只看一個數字！中位數 98 毫秒，P95 卻是 812 毫秒，差了 8 倍，這就是嚴重的長尾。經驗法則：P95 除以中位數超過 3 倍，就是長尾。另外，如果整體延遲比 `expected_response:true` 那行還快，代表錯誤回應在『快速失敗』，把延遲數字美化了。  
> 
> **第四步，看 EXECUTION，這次壓測本身有效嗎？** 這一步最多人忽略。`dropped_iterations` 是 37，而且 vus 的最大值 60，剛好碰到 vus_max 60。這代表 VU 池被用光了，**我們設定的 50 RPS 根本沒打出去**。流量沒打滿，結論就要打折扣。  
> 
> **第五步，看 NETWORK。** 38 MB 除以 2960 個請求，每筆回應大約 13 KB，合理。如果接收速率逼近壓測機的網卡上限，那瓶頸在壓測機，不在受測系統。  
> 
> 五步走完，結論就出來了：P95 違規、8 倍長尾、VU 池見底——**後端在大約 50 RPS 就已經飽和，慢請求把 VU 佔住，壓測端也補不上流量。** 這就是讀摘要和『看摘要』的差別。」

### 【Slide 6 (新增): 延遲拆解：http_req_duration 只算後 3 段】 (預估時間: 11:00 - 13:00)

* **畫面焦點**：上方時間線圖（與 Codelab 同一張），左 3 格灰色（連線準備，不計入 duration，連線複用時 ≈ 0），右 3 格藍色（`http_req_duration = sending + waiting + receiving`，waiting 最深）；下方 4 張診斷卡；底部 `--summary-mode=full` 指令。
* **螢幕動作**：【動作：先圈出上方兩個括號標籤，再由左至右掃過 4 張診斷卡，最後指向底部指令】。

**【口播逐字稿】**：
> 「剛才第三步如果發現延遲有問題，下一個問題就是：到底慢在哪一段？  
> 這裡有一個非常多人搞錯的觀念，請大家看上面這條時間軸。k6 把一次請求拆成六段，但是 **`http_req_duration` 只算後面三段**：sending、waiting、receiving。左邊灰色的 blocked、connecting、tls_handshaking 是請求送出之前的連線準備時間，**完全不算在 duration 裡**。  
> 
> 這代表什麼？如果你的問題出在連線層，例如壓測機的本機埠耗盡、或每次請求都重新做 TLS 握手，**你只盯著 `http_req_duration` 是永遠看不到的**！它只會拉長 `iteration_duration`，以及真實使用者感受到的等待時間。  
> 
> 下面四張診斷卡：blocked 高，多半是壓測機本機埠耗盡、或沒有連線複用；connecting 或 tls 高，是每次都重建連線、或網路 RTT 太長。這兩種都是 duration 看不到的。  
> 真正推高 duration 的是右邊兩張：**waiting，也就是 TTFB，是最常見的後端瓶頸**，慢查詢、連線池耗盡、CPU 飽和，都會反映在這裡，下一步就是拿 Tracing 去找最慢的 Span；receiving 高，代表 Payload 太大。  
> 
> 最後一個實用技巧：k6 預設的精簡摘要**不會列出這六個細分指標**。除錯的時候，請加上 `--summary-mode=full`。你可以自己驗證：把 sending、waiting、receiving 三個平均值加起來，剛好就等於 `http_req_duration` 的平均值。」

### 【Slide 7 (原S6): 超越 HTTP：四大自訂指標型態】 (預估時間: 13:00 - 15:30)

* **畫面焦點**：四個生動的圖示矩陣：Counter（訂單計數器）、Gauge（即時水溫規/並行數）、Rate（成功率圓餅）、Trend（處理時長折線）。
* **螢幕動作**：【動作：依序介紹四種指標類別】。

**【口播逐字稿】**：
> 「k6 的強大之處，在於它不僅能測量 HTTP 通訊層，更能讓我們深入業務語意層！  
> k6 提供了四大自訂指標型態（Custom Metrics），我們需要從 `k6/metrics` 模組引入：  
> 
> 第一個是 **Counter（累計器）**：  
> 它是一個單調遞增的計數器。例如電商系統中，我們想統計『整場壓測總共完成了幾筆成功下單』，或者『觸發了幾次庫存不足』。我們宣告 `const orders = new Counter('orders_total')`，每次下單成功就呼叫 `orders.add(1)`。  
> 
> 第二個是 **Gauge（瞬時狀態規）**：  
> 就像儀表板上的指針一樣，數值可增可減，永遠記錄最新的一個狀態。非常適合用來追蹤『當前記憶體水位』或是『當前排隊中的工作數量』。  
> 
> 第三個是 **Rate（成功率指標）**：  
> 它只接受 0 或 1（布林值亦可）。k6 會自動幫你計算出百分比比率。例如：『結帳成功率是否達到 99%』。  
> 
> 第四個是 **Trend（統計趨勢）**：  
> 這是四大指標中最萬能的瑞士刀！只要你把一個數值（例如毫秒時間）丟進 Trend，k6 在測試結束時就會自動幫你算好 min、max、avg、med、以及最關鍵的 P90 與 P95！極為適合用來記錄自訂的資料庫存取耗時，或是自訂 RPC 遠端調用耗時。」

**【口播逐字稿】**：
> 「很多剛學 k6 的同學常常問：『老師，check、thresholds、還有 expect，到底什麼時候該用哪一個？』  
> 我們把這三部曲放在同一個擂台上做權威對比：  
> 
> 首先，**check() 是代碼級的軟斷言**。它的執行層級在單一請求上。哪怕 check 失敗了，虛擬用戶照樣往下跑，它的作用是把檢驗結果記錄為 Rate 指標，終端機只會顯示成功率。它**不會**讓測試中斷，也**不會**讓 CI/CD 失敗！  
> 
> 其次，**thresholds 是系統級的硬門禁 (Quality Gates)**。它是整個壓測的最高法官！它的維度是全域的，在 `options` 裡面宣告。只要任何一條 Threshold 未達標，k6 測試結束時會亮出大紅字，並直接向作業系統回傳非零錯誤碼，強行中斷 CI/CD 流程！  
> 
> 最後，**expect() 是 BDD 行為驅動風格的語法**（來自 `k6/chai`）。如果你習慣了 Jest、Mocha 的 `expect(res.status).to.equal(200)` 語法，你可以使用它來增加腳本的可讀性。  
> 
> 總結一句話：**日常檢查用 check，決定發版生死用 thresholds！**」

### 【Slide 9 (原S8): 精準控制 API SLO：Thresholds 與 Tags 組合技】 (預估時間: 17:30 - 19:30)

* **畫面焦點**：程式碼展示：為不同標籤端點配置差異化 Thresholds，例如 `'http_req_duration{api_type:critical}': ['p(95)<300']`。
* **螢幕動作**：【動作：圈選大括號內的 Tag 過濾條件】。

**【口播逐字稿】**：
> 「在真實專案中，我們絕不能對所有 API 採取一刀切的標準！  
> 靜態圖片下載延遲 1 秒可能無傷大雅，但如果使用者登入或結帳 API 延遲超過 300 毫秒，那就是嚴重的生產事故！  
> 
> k6 提供了極其強大的 **Tag 標籤過濾門檻**：  
> 大家看代碼中的語法：  
> 我們在發送請求時，加上 `{ tags: { api_type: 'critical' } }`；  
> 接著在 `thresholds` 裡面，我們可以寫下：  
> `'http_req_duration{api_type:critical}': ['p(95)<300']`！  
> 
> 這行代碼的意思是：k6 會在背景自動將打上 `critical` 標籤的請求獨立過濾出來，專門對它們實施嚴格的 P95 小於 300ms 門禁；而其他沒有標記的次要請求，則不受這條嚴格規則約束。  
> 透過 Tags 與 Thresholds 的組合技，你就能為微服務中的每一個關鍵 API，定義出由 SLO 推導而來的精準驗收門檻！  
> 
> 這裡要特別提醒一個很多人會搞混的觀念：**k6 threshold 並不等於 SLO。** SLO 是對真實流量、在一段時間窗口內的目標，例如『過去 28 天，99% 的結帳請求在 500 毫秒內完成』；而 threshold 是發版前、單次測試的門檻，只是 SLO 的替代指標。所以 threshold 通常要訂得比 SLO 更嚴格，留一點安全邊際。**跑一次壓測通過了，只代表這個版本沒有明顯退化，不代表上線後就一定符合 SLO**——真正有沒有達標，還是要看上線後的監控。」

**【口播逐字稿】**：
> 「在我們結束本章進入練習前，我還要傳授大家一個資深工程師的避坑技巧——**即時熔斷機制：abortOnFail**。  
> 
> 試想一個場景：你的 CI/CD 排程了一場 1 小時的耐久測試。結果測試剛跑第 20 秒，後端資料庫連線就爆了，錯誤率衝到 100%。如果沒有熔斷，k6 會傻傻地繼續對著已經陣亡的伺服器狂打剩下的 59 分鐘！這不僅白白浪費了昂貴的雲端運算與 CI Runner 額度，還可能把測試環境卡死。  
> 
> 解決方案就是加上 `abortOnFail: true`！  
> 當特定指標（例如錯誤率大於 10%）觸發門檻時，k6 會毫不猶豫**立即腰斬整個測試**，不再進行後續無效的空跑！同時，我們通常會搭配 `delayAbortEval: '5s'`，給系統 5 秒鐘的預熱緩衝，避免因為剛啟動時的冷啟動抖動造成誤殺。這才是一套成熟、具備成本防禦意識的架構設計！」
